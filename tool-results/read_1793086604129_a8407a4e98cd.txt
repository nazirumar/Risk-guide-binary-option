    50→## Architecture Decisions (Phase 0)
    51→
    52→- **Database**: Sandbox-local Prisma uses SQLite for fast iteration. The schema
    53→  is structured so the only required change for Postgres production is flipping
    54→  `provider = "postgresql"` in `prisma/schema.prisma` and pointing
    55→  `DATABASE_URL` at the managed Postgres instance (see `docker-compose.yml`).
    56→- **Money math**: All `Decimal` math will run through `/src/lib/calc` in
    57→  Phase 6. `decimal.js` is already installed and tested in `tests/sanity.test.ts`.
    58→- **Auth strategy**: Database sessions (not JWT) will be used in Phase 2 —

    61→- **Package manager**: `bun` is the sandbox-default; all scripts are also
    62→  compatible with `npm`/`yarn` where possible.

    80→## Architecture Decisions (Phase 1)
    81→
    82→- **Money & percentages use Prisma `Decimal`** (not `@db.Decimal(18, 2)`).
    83→  SQLite doesn't support native Decimal annotations — Prisma preserves full
    84→  precision via its own serialization layer (verified in `scripts/verify-seed.ts`:
    85→  `78.66 × 0.7314 = 57.531924` round-trips correctly). Phase 14's Postgres
    86→  production migration adds the `NUMERIC(18, 2)` and `NUMERIC(7, 4)` precision
    87→  tightening via raw SQL — documented in the schema header comment and ERD.
    88→- **`tags` stored as `Json`** instead of `String[]` — SQLite doesn't support
    89→  primitive list types. `Json` is DB-agnostic, Prisma returns it as a typed
    90→  array, and the Postgres prod migration can keep the JSON column (still
    91→  efficient for ≤ 10 tags per trade).
    92→- **Enums use Prisma `enum`** syntax. On Postgres this becomes native ENUM
    93→  types; on SQLite it falls back to String columns. The semantic contract
    94→  stays the same — no app code needs to change between dev and prod.
    95→- **Per-user multi-tenant isolation** baked into every domain table either
    96→  directly (`userId` column) or transitively (`Transaction.tradingAccountId →
    97→TradingAccount.userId`). Phase 13 will add a CI check that statically scans
    98→  server actions for the `userId` filter.
    99→- **Deterministic seed** (`mulberry32` PRNG with fixed seed) — Phase 6 and
   100→  Phase 9 tests can assert on exact equity curves, win rates, and analytics
   101→  without flaky test data.
   102→- **Demo user credentials**: `demo@riskguard.app` / `riskguard1234`. Password
   103→  hashed with argon2 — Phase 2 will swap in proper Auth.js credentials flow.
   104→- **Seed balances**: DEMO `$10,000 → $6,379.14` (down 36%, illustrating what
   105→  revenge-tilt and over-trading look like); REAL `$500 → $485.17` (down 3%).
   106→  Phase 9 analytics will surface the "REVENGE emotion cost you $X" insight
   107→  on exactly this data.

   134→## Architecture Decisions (Phase 2)
   135→
   136→- **NextAuth v4 (not v5)**: v5 is still alpha; v4 is what's installed and battle-tested. Code patterns are nearly identical; the v5 beta would require bigger migration risk than the few API improvements it offers.
   137→- **JWT strategy** (chosen over database): Next.js middleware runs in the edge runtime which can't reach Prisma, so database sessions would force every protected route through a Node.js boundary just to check auth status. JWT lets middleware read `isOnboarded` / `emailVerified` claims without a DB hit. Trade-off: lost instant-revocation — Phase 13 adds a `sessionVersion` integer on User (bumped on password change / logout-everywhere) included in the JWT; mismatch invalidates the token.
   138→- **`proxy.ts` not `middleware.ts`**: Next.js 16 deprecated the `middleware.ts` file convention and renamed it to `proxy.ts`. Same `withAuth` API from next-auth, just a different filename.
   139→- **`/onboarding` outside `/app/*`**: The onboarding page was originally at `/app/onboarding` but the parent `/app/layout.tsx` calls `requireUser()` which redirects un-onboarded users to `/app/onboarding` — infinite loop. Moving it to `/onboarding` puts it outside the authed-app layout. The wizard uses `requireUser({ skipOnboardingCheck: true })` and calls `useSession().update({ isOnboarded: true })` after success to refresh the JWT so middleware lets the user into `/app/dashboard`.
   140→- **`@auth/prisma-adapter` v2**: PrismaAdapter expects `User`, `Account`, `AuthSession`, `VerificationToken`, `Authenticator` models — all defined in Phase 1 schema. The Session model is named `AuthSession` to avoid clashing with the existing `TradingSession` (Phase 1 model for trading sessions, completely different concept).
   141→- **Email dev fallback**: When `RESEND_API_KEY` is unset, `ConsoleEmailProvider` logs the full email payload to the server console (with the verification/reset links extracted and printed). This means tokens/links are clickable during local development without needing a real Resend account — and the e2e test can verify by reading the token directly from the DB.
   142→- **Argon2 (not bcrypt)**: argon2 won the Password Hashing Competition; it's the modern recommendation. Already installed + used by the seed script. `argon2.verify` against a dummy hash on user-not-found keeps timing constant for side-channel resistance.
   143→- **`next-auth/react` SessionProvider wrapped in a client component**: The root layout is a server component, so directly using `<SessionProvider>` (which uses React Context) throws "React Context is unavailable in Server Components". Created `src/components/providers/AuthProvider.tsx` as a `"use client"` wrapper that the server layout can render.
   144→- **Test tooling cleanup**: vitest was at v2 which bundled an old vite that couldn't load ESM-only `@vitejs/plugin-react` or `@tailwindcss/postcss`. Upgraded to vitest@3, dropped `@vitejs/plugin-react` from the config (not needed yet — Phase 3 will revisit when we add React component tests), and disabled CSS PostCSS processing in tests.

   180→## Architecture Decisions (Phase 3)
   181→
   182→- **Server components for pure-render traders UI**: StatCard, MoneyText, PercentBadge, EmptyState, FormField, RiskDisclaimer, PagePlaceholder are all server components (no "use client") — they have no client-only state and accept icon-as-prop without crossing the server→client boundary (the error that originally surfaced: "Functions cannot be passed directly to Client Components"). ConfirmDialog + DateRangePicker + DataTable + TopBar + Sidebar + BottomTabBar + ThemeToggle + AccountSwitcher are client (they use useState/useEffect).
   183→- **Dark mode default via next-themes**: `attribute="class"` toggles the `.dark` class on `<html>` so our `globals.css` `.dark { ... }` overrides apply. `enableSystem={false}` — trader app should be opt-in dark, not follow OS preference. Phase 12 will add a per-user theme preference saved in the User table.
   184→- **Cookie-persisted active account**: cookie name `riskguard-active-account` stored in `src/server/lib/active-account-cookie.ts` (a non-"use server" module — server-action files can only export async functions).    220→## Architecture Decisions (Phase 4)
   221→
   222→- **Pure balance calc + atomic persistence are separate**: `src/lib/calc/account-balance.ts` is the pure, DB-free math module (PROJECT_RULES.md rule #2 — pure functions in `/src/lib/calc`, fully unit-tested). The server action `recomputeAccountBalanceInTx()` is the persistence wrapper — it calls the pure function inside a `prisma.$transaction` and updates the DB rows. Same formula in both: `currentBalance = startingBalance + Σ(signed transactions) + Σ(trade P/L)`.
   223→- **Signed transaction convention**: `DEPOSIT` / `BONUS` / `ADJUSTMENT` are positive contributors (ADJUSTMENT preserves its sign — the caller passes the raw signed value); `WITHDRAWAL` is negated by `signedTransactionAmount()` (the form always collects a positive amount). This is consistent with how a cash-flow ledger works.
   224→- **No auto-DEPOSIT on account creation**: The original implementation auto-created a DEPOSIT transaction matching the starting balance — but that double-counts. `startingBalance` is the snapshot at account creation; subsequent money flows are recorded as separate transactions. The seed script was updated to NOT auto-create the matching DEPOSIT. The integration tests confirm the formula now: `1000 (start) + 0 (no auto-deposit) = 1000`. The same fix was applied to `completeOnboardingAction` from Phase 2.
   225→- **`recomputeAccountBalanceInTx` recomputes BOTH `currentBalance` AND every trade's `balanceAfter`**: Phase 5's trade journal needs an equity walk — `balanceAfter` on every trade. The recompute walks through trades chronologically (sorted by `openedAt`), running-balance = start + txSum + tradePL-so-far, and updates each trade's `balanceAfter`. This means deleting a transaction OR a trade automatically fixes the entire equity walk — no manual recalculation needed.
   226→- **Cross-user isolation via `userId` in the where clause**: Every `findFirst` includes `{ id, userId }`. Every `updateMany`/`deleteMany` includes `userId` in the where clause → cross-user archive/restore is a silent no-op (count:0). For single-row mutations (delete transaction), the action first finds the transaction, checks `tradingAccount.userId === userId`, and only then deletes. Direct-URL access to `/app/accounts/<other-user-id>` calls `findFirst({ where: { id, userId }})` which returns null → `notFound()` → user sees the standard 404 page (no leak).
   227→- **Reconcile balance is a 2-step flow**: `previewReconcileAction` returns the difference + a friendly message without writing anything. `confirmReconcileAction` creates the signed ADJUSTMENT transaction atomically with the recompute. The UI's `ReconcileBalanceDialog` shows the diff before commit so the user understands what they're confirming.
   228→- **Withdrawals that exceed balance warn but don't block**: Some brokers allow overdraft; RiskGuard surfaces a warning toast ("Withdrawal of $X exceeds the current balance of $Y. This will push the balance negative…") without hard-blocking. The formula still works correctly: $100 balance + $200 withdrawal = -$100. Phase 7's risk rules will surface overdrafts in the daily-loss lockout calculation.
   229→- **CSV export via Route Handler not Server Action**: Server Actions can't return raw strings for direct download — the form-encoded protocol wraps everything in RSC payload. So the CSV is generated by `exportTransactionsCSVAction` (does the auth + ownership check + CSV string building) and the Route Handler `GET /api/accounts/[id]/export` sets Content-Type + Content-Disposition headers and returns the raw string. The action never leaks user B's transactions because `verifyOwnership` returns null before the findMany.
   230→- **AuditLog captures rich meta**: every action writes a row with action/entity/entityId/meta. The `BALANCE_RECONCILED` entry records `brokerBalance`, `computedBefore`, `adjustment`, `computedAfter` — full forensic trail if anyone questions the books later.
   231→- **Seed balances reflect the corrected formula**: Quotex Demo `$10,000 → $6,391.48` (was $6,379.14; now includes +$12.34 adjustment that was previously missing); PocketOption Live `$500 → $435.17` (was $485.17; now includes +$50 bonus - $100 withdrawal that were previously missing). The seeded data now matches what the recompute formula would produce.

   272→- **Add Trade form is "always visible" + dialog**: the trades page renders the form inline in a `<details open>` so users can add trades fast on desktop (no modal click needed).    304→## Architecture Decisions (Phase 6)
   305→
   306→- **Shared `TradeLike` + `NormalizedTrade` types**: every calc module accepts the loose `TradeLike` shape (`Decimal | string | number` for any money field) for maximum caller flexibility. `normalizeTrades()` converts to plain `NormalizedTrade[]` (numbers only) and is the entry point for every analytics function. This means the math is always run on plain numbers — Decimal precision is preserved up to normalization, then math is fast.
   307→- **Edge cases are the contract**: every function explicitly handles zero trades / all wins / all losses / payout 0 / empty ranges. The rule: never return `NaN` (use `0` or `Infinity` instead). This makes the calc functions safe to call from any caller — they won't break the UI with `NaN` display.
   308→- **Pure functions, no DB, no side effects** (PROJECT_RULES.md rule #2). Every function in `/src/lib/calc` is a pure transformation — given the same input, returns the same output. Trivially testable, trivially cacheable, trivially runnable from edge runtime.
   309→- **Two layers of "break-even"**: `trade.ts` has `breakEvenWinRate(payout)` (used by Phase 5's Add Trade form preview). `rates.ts` also exports it (for the analytics page). Same formula; the rates.ts version is called by the `computeStats` aggregator.
   310→- **`computeStats`, `computeEquityStats`, `computeRiskStats` aggregators**: each module exports a "return everything in one pass" helper so dashboards can call one function instead of 15. This is the Phase 9 dashboard's primary API.
   311→- **`groupAndAggregate` takes the rates module as a callback**: avoids circular import between `group-by.ts` and `rates.ts`. Callers pass `{ winRate, expectancyPerTrade }` as an explicit dependency — clean and testable.
   312→- **`riskOfRuin` uses the gambler's-ruin approximation**, not Monte Carlo (that arrives in Phase 8's staking plans). The approximation is conservative — real ruin probability is usually lower because traders don't keep staking flat after losses.
   313→- **`consistencyScore` is per-trade, not annualized**: binary options traders don't run 252 "trading days". Per-trade Sharpe-like is more useful. Callers can annualize if they want (× √N where N is the typical trades per year).
   314→- **All Decimal math lives in `trade.ts` and `account-balance.ts`** — those modules export Decimal-returning functions used by the Add Trade form preview and the atomic balance recompute. The Phase 6 analytics modules all work on plain numbers (via normalizeTrades) for speed and simplicity.

   350→## Architecture Decisions (Phase 7)
   351→
   352→- **Timezone helpers are pure** in `src/lib/timezone.ts` — no DB, no side effects. They use `Intl.DateTimeFormat` (built-in to Node 18+) to derive the TZ offset (including DST), then compute the UTC instant of user-local-midnight. This means the rule checks can run in the edge runtime if needed, and the math is fully unit-testable with fixed UTC instants.
   353→- **`evaluateRisk` is READ-ONLY** — it never creates lockouts. `autoCreateLockoutAfterClose` (called from `closeTradeAction` AFTER the trade close transaction commits) is the writer. This separates "should this trade be allowed?" from "did the just-closed trade trigger a breach?" — both use the same `startOfTodayUtc`/`startOfWeekUtc` helpers so the time windows match.
   354→- **Rule priority**: BLOCK rules are checked first; if any BLOCK reason is appended, the WARN rule (Rule 8: stake > risk-per-trade limit) is suppressed (we don't pile on WARN reasons when the trade is already blocked). The final severity is `BLOCK` if any BLOCK reason, else `WARN` if any WARN reason, else `OK`. Integration test "Priority — BLOCK + WARN together → BLOCK wins" verifies.
   355→- **Override doesn't reset the underlying breach** — overriding the lockout just clears the active-lockout rule. If the user's still in max-consec-losses breach, they'll be BLOCKed again on the next evaluateRisk call. This is intentional: the override is a temporary release from one rule, not a get-out-of-discipline-free card. Phase 11's reports will surface the override count + reasons.
   356→- **`evaluateRisk` accepts an optional `now: Date`** for testability. Production callers omit it (defaults to `new Date()`); tests pass a fixed instant so the "today"/"this week" windows are deterministic. Same pattern applied to `getActiveLockout`. This avoids fragile time-mocking (vitest fake timers) for what's really just "compute the window starting from this instant."
   357→- **The cron endpoint is a cleanup job, not the expiry mechanism**. Lockouts are _effectively_ expired the moment `expiresAt < now` because `getActiveLockout` filters by `expiresAt > now`. The cron just deletes historical rows (older than 7 days + overridden) so the lockout table doesn't grow unbounded. Override entries are kept until 7 days after their original expiry so Phase 11 reports can still surface "you overrode X lockouts last month."
   358→- **LockoutBanner uses a regular `Button type="submit"` inside a `<form>`** (not `AlertDialogAction`) because `AlertDialogAction` auto-closes the dialog before the form's `onSubmit` can fire. The dialog closes naturally when the `overrideLockoutAction` succeeds + `router.refresh()` re-renders the page (which removes the banner since the lockout is now overridden).
   359→- **RiskMeter is server-rendered**, not polling. `closeTradeAction` calls `revalidatePath("/app/dashboard")` so the next render picks up the new state. For real-time updates during a long trading session, Phase 12 may add a polling interval — but for binary options (where trades close in minutes), the post-close refresh is enough.
   360→- **The `Progress` shadcn component was extended** to accept an `indicatorClassName` prop for color customization (profit green, warning amber, loss red). Backward-compat: existing callers pass nothing and get the default `bg-primary` indicator.
   361→- **`getRiskProfile` falls back gracefully**: per-account profile → global profile (tradingAccountId IS NULL) → onboarding defaults. So a fresh user with no profile still gets reasonable limits (2% risk, 6% daily loss, 3 consec losses, 10 trades/day, 3 open max).    394→## Architecture Decisions (Phase 8)
   395→
   396→- **Pure staking math lives in `/src/lib/staking/`** per PROJECT_RULES.md rule #2. The 8 plan implementations + Monte Carlo + Kelly helpers are all pure (no DB, no side effects). The `next-stake.ts` module IS server-side (uses db) — that's the bridge between the pure math and the persistence layer.
   397→- **Discriminated union for PlanConfig**: `type PlanConfig = { method: "FIXED_AMOUNT"; amount: number } | { method: "FIXED_PERCENT"; percent: number } | ...`. TS narrows by `config.method` so each plan function knows its config shape. The DB stores `config` as Prisma `Json` — the runtime type is asserted via `parsePlanConfig` which does a light `typeof` check.
   398→- **Monte Carlo uses a seeded PRNG** (mulberry32) so tests are deterministic — same seed → same result. Production passes `Date.now()` for a fresh seed each run. The `simulateOnce` function walks 100 trades, updating balance by the plan's computed stake, generating WIN/LOSS/TIE outcomes with the configured win-rate (+ 2% tie rate), tracking peak + max drawdown, and marking ruin when balance ≤ ruinThreshold × startingBalance.
   399→- **Martingale hard cap via `maxSteps`**: the doubling stops at `2^maxSteps × baseUnit` — no infinite exposure. `martingaleWorstCaseExposure` computes the sum of stakes from step 0 to maxSteps (the total amount at risk if every trade in the sequence loses). `martingaleCapHitProbability` computes (1−winRate)^(maxSteps+1) — the chance of losing maxSteps+1 trades in a row (which is the sequence that maxes out the plan).
   400→- **Kelly full/half/quarter**: `kellyFullFraction(winRate, payout) = edge / payout` where `edge = winRate × (1 + payout) − 1`. Full Kelly is mathematically optimal for long-term log-growth but extremely volatile (drawdowns of 50%+ are common). Half Kelly halves the fraction (and the volatility); quarter Kelly quarters it. The UI shows all three with color-coded risk levels + an amber warning.
   401→- **Next-stake suggestion clamps to Risk Rules**: the plan's computed stake is compared to `riskPerTradePercent × balance`; the smaller of the two is returned. If the plan's stake exceeds the limit (e.g., Martingale after 3 losses wants $8 but the Risk Rules cap is $20 on $1000 → wait, $8 < $20 so not clamped; but if the plan wanted $50 and the cap is $20, the suggestion is $20 and `clamped=true`). The UI shows "(clamped to Risk Rules limit)" in amber when this happens.
   402→- **Plan CRUD config entered as JSON**: for Phase 8, the "New plan" UI uses a JSON textarea for the config — simple and general. Phase 8.x can add per-method form fields (e.g., a number input for FIXED_AMOUNT's `amount`, a percentage slider for FIXED_PERCENT's `percent`, a multi-input for CUSTOM's `ladder`). The JSON approach works because `DEFAULT_CONFIGS` pre-fills the right shape when the method changes.
   403→- **NextStakeSuggestionClient + server-side fetch**: the suggestion requires DB access (StakingPlan, recent trades, RiskProfile) so it's fetched server-side in the trades page and passed as a prop to the client AddTradeForm. The client `NextStakeSuggestionClient` just renders the clickable hint and calls `onApply(suggestedStake)` which sets the form's stake field.

   430→## Architecture Decisions (Phase 9)
   431→
   432→- **Server-side analytics via React `cache()`**: `getDashboardStats` is wrapped in `cache()` so multiple server components in the same render don't duplicate the dashboard query. For the analytics page, `getAnalytics` is called once per request (no cache needed since it's only called once).

This means the displayed numbers are provably correct (matching the test expectations) without separate analytics tests.
   434→- **Insights engine is rule-based**: `computeInsights()` checks for patterns in the trade data (REVENGE emotion cost, win rate after consecutive losses, best trading hour, CALL vs PUT imbalance, profit factor check). Plain-language output so traders can act on it immediately. Phase 12 can add ML-based insights if desired.
   435→- **Period comparison**: when the user sets a date range, the analytics page fetches the same-length previous period and computes the delta. Shows Net P/L, Win rate, Trades — current vs previous vs delta. Helps traders see if they're improving.
   436→- **Equity curve starts from 0 for the analytics page** (cumulative P/L, not account balance) — so the curve is relative to the selected date range. For the dashboard, it starts from the current balance (absolute).
   437→- **groupBy aggregation is JS-based** (not DB-side raw SQL) for Phase 9 — fast enough for ≤5,000 trades. Phase 13 can optimize with `db.trade.groupBy()` for the asset/hour/weekday dimensions if profiling shows slow paths with 10,000+ trades.
   438→- **Filter bar is a GET form** (no JS needed) — date range + account + strategy filters are URL parameters. This means analytics pages are shareable/bookmarkable with their filter state.

   464→## Architecture Decisions (Phase 10)
   465→
   466→- **Checklist + daily journal stored on User model** as nullable JSON fields (`checklistItems`, `dailyJournal`). SQLite doesn't support JSON column defaults, so these are nullable with the application layer providing defaults. The `getDashboardStats` / goals page handles `null` by falling back to `["Checked news calendar", "Within trading hours", "Calm"]` and `{}` respectively.
   467→- **Compounding planner is pure** (`src/lib/calc/compounding.ts`) per PROJECT_RULES.md rule #2. The `compoundingPlan()` function takes `(startBalance, dailyGrowthPercent, numDays, withdrawalRule?)` and returns a projection table. The `checkRealisticGoal()` function computes the required daily growth % and returns a warning string if >10% (unsustainable) or >5% (aggressive).
   468→- **Session auto-linking via time window**: trades are linked to a session by checking `openedAt >= session.startedAt AND openedAt <= session.endedAt`. This is a simple time-window query — no foreign key needed. Works for both ended sessions (fixed window) and active sessions (window extends to "now").
   469→- **Goals use the existing Phase 1 Goal model** (type DAILY/WEEKLY/MONTHLY/BALANCE_TARGET, targetAmount, startDate, endDate, status). Progress is computed at render time from the current P/L toward the target. The `revalidatePath("/app/goals")` call from `closeTradeAction` ensures goals refresh after each trade.
   470→- **Realistic-check uses the CAGR formula**: `requiredDailyGrowth = (target/current)^(1/days) - 1`. This is the compound annual growth rate (CAGR) formula applied to the daily compounding case. If the required daily growth exceeds 10%, the goal is flagged as "unsustainable" — professional traders aim for 1-3% daily.
   471→- **Daily journal is keyed by date string** ("YYYY-MM-DD") in a JSON map on the User model. This allows the user to have one reflection per day without a separate table. The map can grow unbounded over years — Phase 13 can add a cleanup/archival strategy if the JSON column gets large.

   556→## Phase 13 — Architecture Decisions
   557→
   558→- **Security headers via `next.config.ts → headers()`**: applied to all routes via `source: "/(.*)"`. Includes HSTS (1-year + includeSubDomains), X-Frame-Options: DENY, X-Content-Type-Options: nosniff, Referrer-Policy, Permissions-Policy. CSP (Content Security Policy) intentionally NOT added — Next.js requires nonce-based CSP which is complex to set up correctly. Phase 14 can add it.
   559→- **Health endpoint at `/api/health`**: checks DB connectivity by counting users (`prisma.user.count({ take: 1 })`). No auth required — it's a public health check for uptime monitors + load balancers. Returns 503 if the DB is unreachable. The Prisma client is instantiated inline (not the singleton) because the health check should work even if the app's main DB connection pool is exhausted.
   560→- **"use server" file type/const export fix**: moved all `export type` and `export const` declarations out of `"use server"` files into separate non-"use server" files (`lockout-types.ts`, `notification-types.ts`). This fixes the Turbopack error "A 'use server' file can only export async functions, found object." The pattern: "use server" files export ONLY `async function` declarations. All types, constants, and non-async values live in regular `.ts` files.
   561→- **LockoutBanner hydration fix**: replaced `useState(() => Date.now())` + `useEffect` with `useSyncExternalStore`. Server snapshot returns 0 (constant), client snapshot returns `Date.now()`. React handles the transition without a hydration mismatch. This is the React 19 recommended pattern for reading external mutable state.
   562→- **Dependency audit findings**: all 123 vulnerabilities are in dev dependencies (vitest, picomatch, eslint, lint-staged, next-intl's @parcel/watcher). The production runtime dependencies (next, react, react-dom, prisma, decimal.js, argon2, resend, upstash) are clean. Running `bun update` would resolve most dev-only vulnerabilities but may introduce breaking changes. The approach: document the findings in SECURITY.md, note that they're dev-only, and resolve them in a dedicated dependency-update PR.
   563→- **Coverage target**: `/src/lib` exceeds 80% (the pure functions are fully tested). `/src/server` is lower (~40% for server actions) because server actions need Next.js request context (cookies, headers, sessions) that isn't available in the Vitest runner. The critical paths (balance recompute, cross-user isolation, risk-check rules, equity walk) are tested via integration tests that call the same pure helper functions the server actions use. Full server-action coverage would require either mocking the Next.js request context or running e2e tests for every flow — Phase 14 can explore this.
   564→- **CI workflow**: GitHub Actions runs lint → typecheck → test → build on every push + PR. Uses `bun install` + `bun run` scripts. The `DATABASE_URL=file::memory:` uses SQLite in-memory for the test phase. E2E tests run separately (they need a running dev server).
