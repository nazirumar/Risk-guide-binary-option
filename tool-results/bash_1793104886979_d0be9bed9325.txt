London shifts 0 → +60 (BST) on the last Sunday of March; NY shifts -300 → -240 (EDT) on the second Sunday of March. Asian (Tokyo) has no DST so its boundaries are stable year-round. ### Phase 24 implementation notes

- **Files added**: `src/lib/billing/plans.ts`, `src/lib/billing/provider.ts`, `src/server/lib/require-plan.ts`, `src/server/actions/billing.ts`, `src/app/api/webhooks/paystack/route.ts`, `src/app/api/webhooks/stripe/route.ts`, `src/app/api/cron/billing-grace/route.ts`, `src/app/app/billing/page.tsx`, `src/app/app/legal/terms/page.tsx`, `src/app/app/legal/privacy/page.tsx`, `src/app/app/legal/refund/page.tsx`, `src/components/billing/BillingActionsClient.tsx`, `tests/calc/billing.test.ts`.
- **Files changed**: `prisma/schema.prisma` (3 enums + 3 models + User subscription back-reference), `src/components/shell/nav-items.ts` (add Billing nav item, icon CreditCard).
- **Schema choice**: PART2_NOTES.md suggested a `subscriptionId String?` FK on User pointing to Subscription — but Prisma's 1-1 relation constraint required the FK on the Subscription side (userId, which already exists as a non-null field). Resolved by using a named `@relation("UserSubscription")` where Subscription owns the FK (userId + `fields: [userId], references: [id]`) and User has the back-reference `subscription Subscription?` (no fields/references). The `@@unique([userId])` on Subscription enforces one subscription per user.
- **Plan hierarchy**: FREE < PRO. `requirePlan("PRO")` blocks FREE users; `requirePlan("FREE")` never blocks. The hierarchy array `["FREE", "PRO"]` + indexOf comparison is the pure implementation. The DB-backed `getPlanForUser` reads the Subscription row's plan + status — PAST_DUE subscriptions keep their plan (PRO) during the grace period; EXPIRED subscriptions are treated as FREE by `getPlanForUser`.
- **Webhook idempotency**: the `ProcessedEvent` model stores `(provider, eventId)` as a unique pair. The webhook handler checks this table BEFORE processing — if the event was already seen, returns early. This prevents Paystack/Stripe retry storms from double-applying subscription changes or creating duplicate Payment records. The unique constraint at the DB level also provides a safety net (a duplicate insert would fail, but the check-then-insert pattern means the handler returns gracefully rather than crashing).
- **Grace period**: `GRACE_PERIOD_DAYS = 3` (per spec). The webhook sets `gracePeriodEndsAt = now + 3 days` on a payment failure. The daily cron (`/api/cron/billing-grace`, token-protected) calls `expireGracePeriodsAction` — queries all PAST_DUE subscriptions where `gracePeriodEndsAt < now`, sets plan=FREE + status=EXPIRED + clears the grace timestamp, + writes a SUBSCRIPTION_EXPIRED audit log. Per spec: "never delete data because of a plan change" — the downgrade only changes the plan/status fields, not the user's trades/accounts/transactions.
- **Provider swappability**: the `BillingProvider` interface is minimal (initializeCheckout + verifyWebhookSignature + parseWebhookEvent). `ConsoleBillingProvider` is the dev/test fallback. `PaystackProvider` uses the Paystack Initialize Transaction API + HMAC-SHA512 webhook verification. `StripeProvider` is stubbed (falls back to Console when STRIPE_SECRET_KEY is set — the TODO is documented). Adding Stripe is a matter of writing the provider class + the Stripe webhook signature verification (Stripe-Signature header with the t=,v1= format). No UI changes needed.
- **Legal pages**: generic templates at `/app/legal/{terms,privacy,refund}` — each with a prominent "Important: This is a generic template. Have it reviewed by legal counsel before production use." warning box. The Terms include the risk disclaimer (binary options are high-risk, most traders lose money). The Privacy includes the AI review data-sharing disclosure (only aggregated stats, no email/name/screenshots). The Refund includes the 3-day grace period + cancellation-at-period-end. These are templates — the spec said "clearly marked for legal review."
- **Downgrade preserves data**: per spec, "existing users keep read access to their data after a downgrade (never delete data because of a plan change)." The downgrade (FREE/EXPIRED) only changes the plan + status fields on the Subscription row — all Trade, Transaction, TradingAccount, DailyScore, WeeklyReview, TiltEvent, BalanceCheck, WithdrawalRule rows are preserved. The `requirePlan` helper blocks NEW writes to gated features (tilt detection, Telegram, AI review, etc.) — but reads are always allowed (the helper is only called on create/upgrade actions, not on reads).
- **All phases complete**: Phase 0–14 (Part 1) + Phase 16–24 (Part 2) — the entire RiskGuard project is now feature-complete. 855 tests across 33 files. Production build succeeds with all routes. The app is ready for deployment.
